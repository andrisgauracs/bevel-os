# Port to the Guition JC1060P470-V2 (ESP32-P4): status and how to continue

Work in progress. The port is committed, and the tree now builds **both** boards again: this board and
the original ESP32-S3 VGA machine ("Two boards in one tree" below). Board notes:
`esp32_usb_cd_player/docs/JC1060P470-V2.md`. Pins used by the OS: [main/board_p4.h](../main/board_p4.h).

## Build, flash, drive

- ESP-IDF **v6.1**: in PowerShell run `. C:\Espressif\tools\Microsoft.v6.1.PowerShell_profile.ps1` first.
- `tools\flash.ps1 [-Target esp32p4|esp32s3]` builds (the P4 by default, through the CMake preset of
  that name, in `build-esp32p4/`), stops the serial daemon, flashes over COM13, restarts the daemon,
  prints the log.
- `python tools\bv.py daemon` holds COM13 (USB-Serial-JTAG). Then `bv.py cmd "<line>"`, `bv.py dump out.png`
  (RGB565 screenshot of what the panel shows), `bv.py reset` (sends `reboot`), `bv.py log`, `bv.py quit`.
  New serial commands: `usbdev` (list USB devices), `net`, `stat`.
  The same three things work without a daemon at all - `bv.py direct "<line>" [secs]`,
  `bv.py directdump out.png [nocursor] [secs]` and `bv.py directput local /disk/path`: they open the
  port themselves, so they work in a session that may not start a background process or listen on a
  port (the daemon needs a socket on localhost, which such a session refuses). One board may be
  talked to one way or the other, never by both at once.
- Apps: from a shell with ESP-IDF active, `bash tools/build_apps.sh esp32p4` and
  `bash tools/build_doom.sh esp32p4` (RISC-V, `-march=rv32imafc_zicsr_zifencei -mabi=ilp32f`). The ELFs for
  this board live in `disk/Apps/esp32p4/`; the S3 ones in `disk/Apps/esp32s3/`.
- Each board is a CMake preset (`CMakePresets.json`) with its own build directory and `sdkconfig`
  there, generated from `sdkconfig.defaults` + `sdkconfig.defaults.<target>`. `idf.py` 6.1 reads the
  presets file and takes the first preset (the S3) unless given `--preset` or `IDF_PRESET`.
  `dependencies.lock` is still one file at the top, rewritten for whichever board was built last.

## Two boards in one tree

The ESP32-S3 build was brought back alongside this one rather than replaced by it. How the split works:

- `main/board.h` picks `board_p4.h` or `board_s3.h` and defines `BOARD_HAS_TOUCH / _RTC / _I2C / _AUDIO /
  _SD / _ETH / _CAMERA / _WIFI_REMOTE` and `BOARD_CONSOLE_USB_JTAG`. Code that differs only by what is
  wired tests those flags; code that differs by CPU (exception frames, DWC registers, PIE) tests
  `CONFIG_IDF_TARGET_*`.
- `main/display.h` is the shared surface: `disp_init/put/present/snapshot/cursor`, the true-colour
  overlays, and under `DISP_HAS_SCANOUT` the scan-out stats and copy-mode switch. `main/display_dsi.c`
  is the JD9165 DSI driver (was `main/display.c`), `main/display_vga.c` wraps the old `main/vga.c`.
  `main/CMakeLists.txt` picks the driver, the touch/camera or PIE/diag sources, the app directory and
  the chime per target.
- The S3's beam racing, PIE kernels, `pie.S`, `diag.c`, `vstat`/`copy`/`race` and the scan-out
  benchmarks are all back, behind `DISP_HAS_SCANOUT` / `HAS_PIE`, so the P4 build is unchanged.
- **Verified:** `esp32p4` and `esp32s3` both compile and link under v6.1 (S3 image 1 946 kB in its 3 MB
  partition). **Not verified:** the S3 firmware has not been flashed or run since the split; the VGA
  driver needed one change for v6.1 (`bits_per_pixel` is gone, `LCD_COLOR_FMT_GRAY8` on 8 data lines
  replaces it) and the S3 target now selects newlib explicitly, because v6.1 defaults that chip to
  picolibc where `__getreent` is a macro and the apps need the real symbol.

## Flashing: what was wrong and what works

`idf.py -p COM13 flash` now works (the board is on COM13, USB VID:PID 303A:1001 = its
USB-Serial-JTAG port). The earlier "Failed to connect to ESP32-P4: No serial data received" came and
went with whatever held the port: run `python tools\bv.py quit` first, wait a second, then flash. If
the daemon itself seems dead but the port is busy, it was started with a Python that has no pyserial
- start it with the ESP-IDF venv Python (`C:\Espressif\tools\python\v6.1\venv\Scripts\python.exe`),
which has it. No BOOT+RST was needed.

## Measured on the board with the two-board firmware (commit 60038d2, and again after the
app-loading fix below)

Flashed over COM13; the first boot after the flash took 9.1 s (the drive is rewritten when the
firmware stamp changes), every boot after that reaches the desktop in about 0.4 s. The desktop came
up with: Ethernet link 100 Mbit/s + DHCP address + SNTP time, SD card SC32G
30436 MB mounted at /disk/SD, GT911 touch ready, PCM5102 started, RTC kept the time across the
reboot, Logitech keyboard and mouse enumerated, `dump` screenshot correct (icons, taskbar, clock),
Terminal window opened by a double click through the serial mouse commands, `stat` reports the
compositor and memory.

**Solved: no loadable app ran on this board.** Snake and Doom used to die the same way:

    I (255296) ELF: ELF loader version: 2.1.0
    I (255297) ELF: Too much padding before segment[2], padding: 4240
    I (255298) ELF: elf->entry=0x48490360
    [app] Snake crashed: cause 1 pc 48490360 addr 48490360

The padding line is a red herring: it only says the gap between the two `PT_LOAD`s is wider than the
loader's `ADDR_OFFSET`; the loader keeps the gap and allocates the whole span, which costs a few
kB of memory and nothing else. The same ELFs ran on the S3 build, and that was the clue: it is the
memory the text lands in, not the app.

The cause is the PMP. With `CONFIG_ELF_LOADER_LOAD_PSRAM=y` the loader copies every `PT_LOAD` into
one PSRAM allocation, and with `CONFIG_ESP_SYSTEM_MEMPROT=y` plus
`CONFIG_SPIRAM_PRE_CONFIGURE_MEMORY_PROTECTION=y` ESP-IDF gives the PSRAM heap read-write and **no
execute** bit (`esp_hw_support/port/esp32p4/cpu_region_protect.c`, the region sized by
`esp_psram_get_heap_size_to_protect()`). The bytes were there, the fetch was refused: cause 1 at the
entry, which is exactly what an instruction access fault at `mtval == pc` means. The same ELFs ran on
the S3 build because that chip's region protection never says a word about external RAM
(`esp_hw_support/port/esp32s3/cpu_region_protect.c` has no PSRAM entries at all - the help for
`CONFIG_ESP_SYSTEM_MEMPROT` says it acts on the IRAM0 and DRAM0 buses, which is internal RAM), so
there PSRAM keeps its default permissions and the app text is executable.

The fix is one line, `CONFIG_SPIRAM_PRE_CONFIGURE_MEMORY_PROTECTION=n` in
`sdkconfig.defaults.esp32p4`. On a pre-v3 P4 (this chip is rev 1.x) ESP-IDF deliberately leaves
"External RAM" without PMP entries - note 5 at the end of that same file - so PSRAM ends up with all
permissions and apps can execute there, while the IRAM/DRAM split of **internal** RAM, which is what
holds the OS's own code, stays locked. Espressif's own runtime test for the loader does the same one
level up: `elf_loader/tests/idf_runtime/sdkconfig.defaults.esp32p4` turns off the IDRAM split
because the region the code is loaded into has to be executable. What is given up is the protection
of PSRAM against a badly behaved program; that protection was already weak, because with
`CONFIG_SPIRAM_FLASH_LOAD_TO_PSRAM=y` the OS's own text lives in PSRAM too.

## Camera

- `espressif/esp_video` 2.6.0 from the registry (it supports ESP-IDF 6.1) brings `esp_cam_sensor`
  2.7.0, the ISP pipeline and `esp_ipa` (auto exposure and white balance). The registry's
  `esp_cam_sensor` has **no OV02C10 driver**: `components/ov02c10` is the one from
  `p4_edge_enhancer` (it came with esp_cam_sensor 2.1), with that project's mirror fix, as a
  separate component. Its detect function lands in the linker section `esp_cam_sensor` walks, so
  nothing else is needed; it compiled against 2.7 unchanged.
- `CONFIG_CAM_CTLR_MIPI_CSI_ISR_CACHE_SAFE=y` is required: without it the CSI receiver's state is
  allocated in PSRAM and its DMA refuses it ("dw-gdma: user context not in internal RAM").
- `dont_init_ldo = true`: the display driver already powers the MIPI PHY from LDO channel 3.
- esp_video's ISP pipeline raises its log tag to debug whenever the build allows debug logging and
  then prints statistics every frame; the app turns "ISP" and "ov02c10" back down to warnings,
  or the serial dumps get corrupted.
- The preview is bound by PSRAM bandwidth (panel scan-out and camera DMA share it): shrinking a
  1288x728 frame takes about 18 ms and showing it about 18 ms. The PPA was tried for the shrinking
  and was slower (42 ms: its driver cleans the cache over the whole input frame for every job).
  Showing an overlay a pixel at a time took 34 ms, so `convert()` in `display_dsi.c` now copies
  each run of key colour from the overlay row with one `memcpy`.
- The capture task runs at priority 2 on the system core, below the web server (3), USB, touch and
  the drive, and pauses 3 ms after every frame. At priority 4 it used the whole core and the web
  page stopped answering; switching the web page off from Settings then hung the GUI in
  `httpd_stop`, which now runs in a task of its own (`remote.c`).
- The size drop-down lists the sensor's modes (`VIDIOC_ENUM_SENSOR_FMT`), each also halved and
  quartered: 1920x1080, 1288x728, 960x540, 644x364, 480x270, 322x182. A smaller size is its mode
  shrunk when the picture is saved (each pixel the average of the block it covers), so it keeps the
  mode's preview and frame rate; picking another mode switches with `VIDIOC_S_SENSOR_FMT` while the
  stream is off. 1920x1080 needs 4 MB per buffer: three of them
  and the picture copy take 16.6 MB of PSRAM, leaving about 8.8 MB.
- Not tried yet: daylight colour. In a dim room the 1080p mode comes out darker than 1288x728.

## Things found on the way

- **Crash 1 (fixed):** the USB port watchdog power-cycled the root port with a hub attached:
  `assert failed: device_release ext_hub.c:512`. It now only cycles an empty port.
- **Crash 2 (worked around, cause not proven):** once, the saved context of the sleeping `sdcard` task was
  overwritten with network data (a Syncthing LAN broadcast) and the board reset. Ethernet was not started yet,
  so the data came through the C6. It happened in the one boot where the SD card was mounted while ESP-Hosted
  was still initialising its slot on the shared SDMMC controller. The SD task now waits for
  `ESP_HOSTED_EVENT_TRANSPORT_UP` (`os_c6_link_up`). Four boots since without a crash; that is not proof.
  It also means the C6 joins the Wi-Fi network saved by the CD-player firmware on its own.
- First boot after each flash takes about 9 s (bundled files are rewritten to the drive); the first boot on
  a blank flash took 25 s (format). The boot splash now shows that work stage by stage (see below).
- ESP-Hosted logs `major version mismatch` (host 3.0.10 or 3.1.0, C6 firmware 2.12.13), as in the CD player.
  The dependency lock now resolves esp_hosted to 3.1.0: `^3.0.0` allowed it. Left pinned at 3.0.10 the
  dependency step never finishes - it keeps asking for the Kconfig symbols that only 3.1.0's manifest
  defines (`ESP_HOSTED_HOST_USB_*_MANIFEST`), CMake retries three times and gives up. Wi-Fi over SDIO
  comes up the same either way.
- **Boot splash (`main/boot.c`, `main/boot.h`), measured 17 Nov.** The panel shows a progress panel 1.1 s
  after reset, before the drive is even mounted, and keeps the screen until the desktop is worth clicking.
  Nine stages take the bar; the drive stage has seven blocks of its own, so the ~9 s after a flash is
  visible as `restoring Snake.elf` ... `restoring Doom.elf`. With the hub on USB1 (all times are the log's
  own): hub answered 2.7 s, the keyboard and mouse behind it enumerated 5.7 s, and the desktop was painted
  at 6.0 s with a cursor that moved straight away. Before the splash waited, the desktop was painted at
  4.7 s and the cursor only started moving a second later - same wait, but the gap looked like a frozen
  desktop. First boot after a flash: desktop painted 10.9 s, pointer already there. With the receiver
  plugged straight into the port (no hub) it enumerates at 1.71-1.81 s after reset in all five cold power
  cycles and six reboots taken, the wait ends at once (43-44 ms) and the desktop is up 1.32-1.36 s later
  with the cursor answering from the first frame. With the hub the same stage took 3.1-5.8 s, which is why
  the wait exists at all. With nothing plugged in at all the wait runs its 4 s and the port is power
  cycled once at 1.2 s, because a cold wireless receiver can miss the host's first look at the port; the
  port watchdog is also told not to back off to 8 and 12 s while the splash is waiting. `boottime` on the
  serial port prints the numbers, and the log gained `splash up at`, `splash gone at`, `input settled after`.
- **The pointer froze for two seconds at boot, until the startup sound started (fixed).** Synthesising the
  four system sounds used to take the mixer task 2291 ms of pure arithmetic, and that task runs at priority
  12 on SYS_CORE - above `usb_lib` (10), `hid` and `touch` (8), which live on the same core - so it starved
  them for its whole length. Hence: the cursor stopped answering right after the desktop appeared and started
  again at the exact instant the chime did, the same whether or not the volume was up, because the sounds are
  built either way. Fixed twice over: the build now runs at priority 4 with the mixing priority taken back
  afterwards, and the synthesis itself went from 2291 ms to 40 ms by walking a 2048-entry sine table with a
  phase accumulator and decaying a running envelope, instead of asking for the sine of a growing angle and an
  exponential once per sample. The sound stage also moved forward in the boot, so the chime is ready before
  the desktop is painted rather than about two seconds after it. The boot line `audio: chimes built in 47 ms,
  startup sound peaks at 9663, its last tenth at 56 of 32767` reports the build cost and the sound itself, and
  it earned its place: the first version of the faster synthesis built in 40 ms and was inaudible (its
  per-sample decay factor left out the sample rate, so the notes died two samples in), and the second drained
  every note to silence about halfway through, because a Q15 decay factor this close to one rounds away a step
  that stalls once it falls below one count. The whole-signal peak looked fine in both broken builds; the peak
  of the last tenth is where the difference shows - zero when the tail is gone, 56 now. Two seconds of mouse
  movement during boot used to drag the pointer before it was ever drawn; pointer input is now dropped while
  the splash owns the screen, so the cursor starts where the window manager put it - the middle.
- Firmware uses newlib (`CONFIG_LIBC_NEWLIB`), because apps import `FILE`/`errno`/`_ctype_` by name.
- The toolchain's libgcc is not position-independent: Doom is linked without it and imports those routines
  from the OS (`LIBGCC_LIST` in `app_loader.c`).
- **Apps would not run at all (fixed):** the PMP left the PSRAM heap without an execute bit. See the
  section with that name above; the one line in `sdkconfig.defaults.esp32p4` is the whole fix.
- **The Doom app in this repository did not compile** (`os->msg(...)`: the API member is `msgbox`),
  and it asked for the true-colour layer *before* opening its window, when the OS has no canvas to
  hang a layer off. Both fixed in `apps/doom/doom_bevel.c`, and the window is now opened at
  `DOOMGENERIC_RESX * 2` x `DOOMGENERIC_RESY * 2` so the layer is exactly the size the drawing loop
  assumes. `disk/Apps/esp32p4/Doom.elf` had been built from an older revision, and that one drew the
  title page as noise: its window was not 640x400, so the loop that turns each game pixel into a 2x2
  block wrote its rows with the wrong stride. The rebuilt ELF (357 984 bytes) is correct. Every ELF
  in `disk/Apps` has been rebuilt since.
- **Doom for the S3 target did not link (fixed)**: `ld` asserted (`BFD ... assertion fail
  elf32-xtensa.c:3301`) with both the esp-14.2.0 and esp-15.2.0 toolchains. Linking each engine
  object alone with `crt.o` + `doom_bevel.o` found `m_fixed.o`: `FixedDiv` divides 64-bit numbers,
  which is a call to libgcc's `__divdi3` (an `R_XTENSA_PLT` relocation), and `-lgcc` put libgcc's
  non-PIC copy of it into the shared ELF. The S3 build now links without libgcc, like the P4 one,
  and imports those routines from the OS; `app_loader.c` exports `__divsf3` as well on the S3,
  where Doom needs single-precision division from libgcc. All 44 imports of the S3 `Doom.elf` are
  in the loader's table, and the S3 firmware builds with it. `doom_bevel.c` again dithers into the
  64-colour canvas where there is no true-colour layer (the code the first S3 build had), so the S3
  gets a game rather than a message. Seen running on an S3 devkit (without the VGA DAC: through
  serial screenshots): the demo plays, dithered, in a 640x400 window. It needed one more change:
  the zone heap is 4 MB on the S3 (`-mb 4`, as in its first build), where the P4's 8 MB left Doom
  without memory and it quit before opening its window.
- **S3 checks on a second devkit (no VGA DAC built yet, so through the serial channel):** the
  firmware boots, the scan-out runs with no late lines, USB keyboard and mouse enumerate, and
  Settings (with the drop-downs), Files (Up, path, Refresh) and the terminal work. Settings was 8
  pixels wider than the 640-pixel screen and now fits it. This devkit's CH340 bridge lost about one
  byte in 3500 at the console's 2 Mbaud, whatever the pacing, so the S3 console now runs at 460800
  (no losses seen); `bv.py` also fetches screenshots over a UART in checked bands of rows (`dump
  band y0 rows`, which snapshots only those rows, so it works even while Doom has the PSRAM), and
  the `crc <path>` command checks a file sent with `put`. The web page and Wi-Fi were not tried on
  the S3 (no network saved on it).
- Building the S3 firmware also found `remote_files.c` using `SD_ROOT`, which only boards with a
  card reader define; fixed.
- A program that keeps the CPU busy (Doom's main loop runs at the priority the serial task has) can
  overflow the console's transmit ring in the middle of a `dump`, and the last couple of kB of the
  screenshot never arrive. `bv.py directdump` now says so and fills the missing rows with black.
- `disk/Apps/<target>/*.elf` are tracked files, and the drive re-copies them only when the firmware
  stamp changes. After rebuilding an app, either flash again or push the file:
  `bv.py directput disk/Apps/esp32p4/Doom.elf /disk/Apps/Doom.elf` (358 kB in 10 s).
- Building the apps needs the compiler on the PATH of the shell that runs the script: the IDF
  PowerShell profile does not put it there for `bash`, and the `bash` on this machine is the WSL one
  (it does not inherit the Windows PATH). What works from PowerShell:
  `$env:PATH = "C:\Espressif\tools\riscv32-esp-elf\esp-15.2.0_20251204\riscv32-esp-elf\bin;" + $env:PATH`
  and then `& "C:\Program Files\Git\bin\bash.exe" -c "tools/build_doom.sh esp32p4"`.
